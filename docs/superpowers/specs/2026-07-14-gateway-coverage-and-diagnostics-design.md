# 票价网关覆盖率与供应商降级诊断设计

**状态：** 已实施；供应商覆盖仍受配额与风控限制
**日期：** 2026-07-14

## 实施前复现结论

本地新计划 `8X2B7W` 使用两名参与者、仅航班、12 个候选城市，产生 24 个不同的路线组。计算在 26.6 秒完成，但结果为 `PARTIAL_ESTIMATE_FALLBACK`。已展示的三张推荐卡中，北京出发三行显示“飞猪参考价”，上海出发三行显示“估算”；估算原因包含两次 `PROVIDER_INVALID_RESPONSE` 和一次 `PROVIDER_RATE_LIMITED`。

`GET /healthz` 返回 200，只能证明网关可达。经已认证网关直接探测，上海→武汉航班返回 200 和 10 条规范化结果；上海→无锡航班稳定返回 502 `PROVIDER_INVALID_RESPONSE`。因此，结果页没有把真实行错误降级；至少一类供应商响应无法在网关边界完成规范化。当时网关没有请求级脱敏诊断，因此无法从日志还原 24 个路线组的完整结果分布。

## 目标与边界

1. 在不记录原始供应商响应、票价、城市名、参与者身份或密钥的前提下，定位每个请求的供应商错误、空结果、无路线、上游不可用和规范化失败。
2. 对 live `data.itemList` 响应逐项规范化；一条异常条目不能丢弃同一响应中的有效真实路线。
3. 供应商已返回 `PROVIDER_RATE_LIMITED` 时，主应用不再对同一模式立即发起第二次网关请求；估算行保留该稳定原因。
4. 维持网关的既有职责、单并发、相同请求合并、5 秒/15 秒冷却、成功缓存，以及主应用的确定性选路和评分。

不承诺用代码绕过供应商配额或风控，也不改变候选城市生成、路线选择、评分、DeepSeek、身份持久化或结果页的真实/估算标签规则。

## 方案

### 1. 网关只记录结构化脱敏诊断

在 FlyAI 适配器和网关启动边界注入一个可替换的诊断记录器。每次供应商调用只记录以下元数据：

- 请求交通方式；
- 由既有规范化缓存键计算的不可逆路线指纹；
- 最终稳定错误码或 `SUCCESS`；
- 顶层对象、`data` 对象和第一层条目使用的字段名；
- `itemList` 总数、成功规范化数、丢弃数；
- 被丢弃条目的缺失字段名或校验类别；
- CLI 进程错误分类。

路线指纹只用于由掌握探测清单的运维人员把“出发地 × 候选城市 × 方式”与诊断事件关联；日志本身不包含参与者身份或原始路线字段。不记录城市名、服务编号、票价、时间、URL、原始 stdout/stderr、供应商错误正文或令牌。日志用于运行时排障，不进入缓存、HTTP 响应或数据库。

### 2. live 响应逐项校验与稳定分类

保留对响应外层 `data.itemList` 的结构检查，但将条目校验从“整个数组必须全部通过”改为“每条目独立校验”。有效条目继续被转换为现有 `GatewayTravelOption`；无价格、时间、车次/航班号或不一致的条目被丢弃并记录脱敏原因。

若 `itemList` 非空但没有任何有效条目，适配器返回 `PROVIDER_INVALID_RESPONSE`；若响应不是可识别的列表，则仅从状态和错误类别文本中映射既有稳定码（无路线、无票、限流、上游不可用）。未知或无法安全分类的响应仍为 `PROVIDER_INVALID_RESPONSE`。不向客户端暴露供应商文本。

### 3. 主应用取消限流即时重试

`searchGatewayWithRetry` 仅对网关不可达、网关超时、供应商超时、供应商不可用和上游不可用做既有一次重试。`PROVIDER_RATE_LIMITED` 由网关冷却处理；主应用收到该码后立即创建带同一失败原因的估算行，不再增加同轮请求压力。

当前批量编排会把某一模式的稳定失败转换为带 `failureReason` 的估算行，因此它不会再进入后续批量重查；本次只删除该模式内部的即时重试。这样不会把供应商冷却期间的同一模式请求放大为第二次上游调用。

## 数据流与体验

```text
FlyAI CLI
  -> gateway adapter: classify / per-item normalize / redacted diagnostic
  -> gateway HTTP: normalized real options or stable error code
  -> main provider: one retry only for transient non-rate-limit failures
  -> calculation: real row or estimated row retaining failureReason
  -> result card: “飞猪参考价” or “估算 · 原因 <stable code>”
```

`/healthz` 的语义保持不变：仅表示网关进程可访问。结果页只有 `completed` run 才进入；真实行继续显示“飞猪参考价”，估算行继续显示“估算”及稳定原因。

## 验证

1. 网关适配器测试：混合有效/无效 live 条目保留有效行；全无效条目返回 `PROVIDER_INVALID_RESPONSE`；错误信封映射为现有稳定码；诊断不含原始值或敏感文本。
2. 主应用测试：`PROVIDER_RATE_LIMITED` 不在同一模式内即时重试，估算行保留该码；其他既有可重试错误保持一次重试。
3. 网关服务测试：诊断记录只包含允许字段，且不改变响应、缓存、合并或冷却行为。
4. 回归：根项目与网关各执行 `lint`、`test`、`build`。
5. 现场复验：等待供应商冷却后运行一个新完整计划，输出“出发地 × 候选城市 × 方式”的真实行、空结果和稳定错误码计数；分别核对“飞猪参考价”和“估算”展示。真实移动设备日期/时间原生选择器验收不属于本次代码改动，仍需单独完成。

## 风险与后续判断

供应商公开文档未给出可用于调度设计的固定配额。即使完成本修复，单供应商、单并发和 24 个独立路线组仍可能受供应商实际额度限制。若新日志显示规范化失败已消失但限流仍主导降级，应单独评估产品层面的异步计算、持久化缓存或候选集策略；这些属于更改交互和推荐覆盖范围的架构决策，不在本规格内。
