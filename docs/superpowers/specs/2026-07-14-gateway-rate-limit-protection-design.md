# 票价网关限流保护设计

**状态：** 已批准，待执行
**日期：** 2026-07-14

## 问题

一次计划计算会查询多个“出发城市 × 候选城市 × 交通方式”组合。当前网关虽有 4 路并发、成功结果缓存和一次即时重试，但同一缓存未命中的请求可并发穿透到上游；`PROVIDER_RATE_LIMITED` 还会立即再请求一次。主应用也可为同一计划同时创建多个 `running` 计算。这些行为会放大 FlyAI/飞猪的频率或风控限制。

## 目标与非目标

- 降低上游限流与估算降级的概率，宁可使单次计算更慢。
- 同一计划在已有计算进行时只能保留一个运行中的计算。
- 保留真实票价、估算降级、确定性排序和现有网关安全边界。
- 不承诺供应商在额度耗尽或风控拦截时一定返回实时票价；不尝试绕过供应商限制。
- 不变更候选城市、路线选择、评分、DeepSeek 调用或持久化身份责任边界。

## 方案

### 网关：串行、合并与冷却

1. 将 `FifoLimiter` 的默认并发从 4 降为 1，所有 FlyAI 调用全局串行。
2. 在 `TravelSearchService` 维护按既有标准缓存键索引的 in-flight Promise。相同请求在结果未缓存前共享一次供应商调用；无论成功或失败都在 settled 后移除该 Promise。只有成功的规范化响应进入 TTL 缓存。
3. 移除 `PROVIDER_RATE_LIMITED` 的即时重试。首次限流后，网关进入 5 秒全局冷却；如果冷却后的下一次供应商调用再次限流，冷却延长到 15 秒。冷却期间排队请求不调用供应商，待冷却结束后再由单并发队列执行。
4. 超时、上游不可用仍维持现有最多一次重试；冷却仅针对 `PROVIDER_RATE_LIMITED`。

网关不暴露供应商原始错误、额度或密钥。它只继续返回稳定的 `PROVIDER_RATE_LIMITED`，由主应用保留在估算行的 `failure_reason`。

### 主应用：同计划计算互斥

1. 在验证参与者令牌后、创建 recommendation run 前查询该计划是否已有 `status = running` 的 run。
2. 如果存在，API 返回 `409 CALCULATION_IN_PROGRESS`；不创建第二个 run，不向网关发票价请求。
3. Supabase 与内存 fallback 均执行这个互斥规则。用户可见文案为“正在查询票价并生成结果，请稍后自动刷新。”
4. 已有结果页的 `running` 展示与局部刷新逻辑保持不变；只在 `completed` 展示结果。

## 体验与失败行为

- 发起人重复点击：按钮本地禁用；跨设备或重复 HTTP 请求由服务端 409 兜底，页面显示现有的生成中提示而非“计算失败”。
- 冷却会让完成时间延长。若上游仍限流，第二轮查询或后续计算才会走既有估算；界面继续明确显示“部分数据为估算”和稳定原因。
- 网关 `/healthz` 仅表示服务可达，不能代表上游已解除限流。

## 验证

- 网关单元测试：默认并发为 1；同 key 并发查询仅调用 provider 一次；首次和再次限流分别施加 5 秒、15 秒冷却；限流不会即时重试。
- 主应用测试：Supabase/fallback 的运行中计划返回 `CALCULATION_IN_PROGRESS`，且不新增 run 或 provider 查询。
- 回归：根项目及网关各自运行 lint、test、build。
- 手动：等待冷却窗口后以一个新计划重算，确认真实行仍为“飞猪参考价”，未获实时数据的行仍明确标注估算原因；不将一次成功当成供应商配额保证。
